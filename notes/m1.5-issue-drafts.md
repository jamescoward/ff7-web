## 1. Runner: memory card slot and in-memory save/restore

**Outcome**
- The headless runner can put a 128 KiB card in slot 1 and read it back.
- It can save and restore the whole emulator state in memory, through the core's own functions.
- The restored state replays bit-identically.

Nothing is written to disk. Save states are never stored or uploaded, and they exist only within one run.

**Milestone** M1.5

**Allowed paths** `runner/` (`frontend.c`, `backend.js`, `build.sh`, tests), `notes/`, `STATUS.md`

**Acceptance (Tier 1)**
- **Card round trip:** a synthetic blank card goes into slot 1 and reads back identical.
- **Card visible to the program:** a new homebrew fixture reads its card status through the BIOS. If that turns out too large for this issue, a simpler program-visible check will do.
- **Determinism:** run `pad-echo` to frame 30 with input, save, run 60 frames and hash them. Restore, run the same 60 frames, and get identical hashes. Restoring twice gives the same result again.
- **No disk:** an attempt to write a state to disk throws. The API only takes and returns bytes.

**Context** `runner/frontend.c`, `core/web/frontend.c` (which already exposes `fe_card_ptr`); libretro `retro_serialize`.

## 2. Save descriptions and card generator (Tier 1 half)

**Outcome**
- A JSON **save description** format with a schema, and a pure-JS generator: `(baseline savemap bytes, description) → savemap → FF7 checksum → save block → 128 KiB card`.
- The layout table cites a public source for every entry.
- In Tier 1 the baseline is synthetic. Reading the real baseline from the disc is issue 7's job, inside the sandbox.

**Milestone** M1.5. **Needs** PR #29 merged.

**Allowed paths** `runner/savegen/` (new), `harness/saves/` (descriptions), `harness/schema/save.schema.json`, `notes/`, `STATUS.md`

**Acceptance (Tier 1)**
- Schema tests:
  - valid and invalid descriptions;
  - unknown fields are rejected;
  - numbers only, no free text beyond a short ASCII label.
- Each description field lands at its documented offset with the right size, sign and byte order.
- **FF7 checksum** test vectors: either taken from public documentation, or derived and stated in the notes. They are numbers, not real saves.
- **Card format:**
  - 16 frames;
  - directory entries and their XOR checksums;
  - the block header with a blank original icon and an ASCII title;
  - it passes `web/js/memcard.js` validation.
- **No game bytes:**
  - a synthetic baseline of a fixed pattern;
  - every byte of the output is pattern, description value, checksum or card-format constant;
  - the test enforces this.
- `notes/<n>-save-format.md` gives every offset and its source. No code is copied from save editors or decompilations.

**Unknowns to settle**
- How FF7 lays out its saves within card blocks.
- The exact checksum.
- **Research:** the wiki domains are now allowed for new sessions.

## 3. Sandbox runner and attack tests (`needs-owner`)

**Outcome**
- A script that runs the untrusted build (runner + scenarios) in a container:
  - no network (`--network none`);
  - the disc mounted read-only;
  - a read-only root filesystem;
  - CPU, memory, process-count and time limits;
  - no environment variables passed in;
  - one size-capped output directory.
- Attack tests show these hold. **This is M1.5's stop condition.**

**Milestone** M1.5

**Allowed paths** `harness/private-eval/sandbox/` (protected), `notes/`

**Acceptance (Tier 1, with a fake "disc" file of random bytes)**
- Hostile test programs, each run in the sandbox, try to:
  - make HTTP, DNS and raw socket connections;
  - reach `169.254.169.254` (cloud metadata);
  - read environment variables and runner credential files;
  - write outside the output directory, or write to the disc;
  - write more output than the cap allows;
  - fork-bomb, use too much memory, or sleep forever.

  Each attempt must fail, and the sandbox must report the limit it hit.
- A normal Tier 1 scenario still runs inside the sandbox and gives the same result as outside it.
- The script is pinned: the image by digest, and the container tool's version recorded.

**Context** `docs/SECURITY.md` (trust boundary), `docs/AUTOMATION.md` Tier 2.

## 4. Tier 2 result schema and trusted validator (`needs-owner`)

**Outcome** Trusted code turns whatever the sandbox wrote into a bounded summary:
- per scenario: name, pass/fail, numbers, and small integers;
- a cap on the number of scenarios per run;
- everything else is dropped.

Only this summary is ever printed or posted.

**Milestone** M1.5

**Allowed paths** `harness/private-eval/validate/` (protected), `harness/schema/tier2-result.schema.json`, `notes/`

**Acceptance (Tier 1)**
- Fuzz tests with hostile output, all rejected or truncated by rule:
  - huge files;
  - deep nesting;
  - long strings;
  - text hidden in numbers (floats with payload digits, out-of-range integers);
  - extra fields;
  - non-UTF-8 bytes;
  - symlinks in the output directory;
  - more scenarios than allowed.
- Valid output passes through unchanged.
- The summary has a fixed maximum size, and a test checks it.

## 5. Tier 2 workflows (`needs-owner`)

**Outcome**
- **Untrusted build job** (`pull_request`, no secrets): builds the core, the runner and the scenarios, and uploads them as an artifact.
- **Trusted job** (`workflow_run`, runs only for same-repo PRs):
  1. fetches the disc from R2;
  2. runs the artifact in the sandbox from issue 3;
  3. validates the output with issue 4's validator;
  4. posts a `tier2` check run with the summary.
- The disc never touches the Actions cache or artifacts.

**Milestone** M1.5. **Needs** issues 3 and 4 merged, plus owner setup.

**Allowed paths** `.github/workflows/tier2*.yml` (protected), `notes/`

**Acceptance**
- **Fork and non-collaborator PRs:** the trusted job skips them, with a test against the event payload.
- **Untrusted artifact:**
  - it is downloaded into an empty directory;
  - it is never executed outside the sandbox;
  - its size is checked.
- **Clean-up:** the disc is deleted at the end, even on failure.
- **Dry run:** a deliberately failing homebrew scenario shows up as a red `tier2` check, with only the summary in the log.

**Decision needed (owner): R2 credentials.** R2 doesn't accept GitHub's OIDC tokens natively. Options:
- **(a)** A read-only R2 token, scoped to the disc bucket, stored as a secret of a GitHub **environment** that only `main` may use. The trusted job runs from `main`, so it can read it; PR workflows can't. This is the simplest option, but `SECURITY.md` says "OIDC", so it needs a small wording change there.
- **(b)** A small Cloudflare Worker that checks the GitHub OIDC token and returns a short-lived presigned URL. This keeps OIDC, but it's more to build and run.

Recommendation: (a).

## 7. Scenario format 2: boot from a generated save

**Outcome** `boot: { save: "<description name>", slot: 1 }`. Inside the sandbox, the runner:
1. reads the **baseline savemap from the disc** (the game's new-game data);
2. builds the card (issue 2) and puts it in slot 1;
3. boots once per run to the title screen and takes an in-memory snapshot (issue 1);
4. for each scenario: restores the snapshot, swaps in that scenario's card, and plays the **load-slot-1** input sequence. It waits on detected screens (title, menu, field loaded), not fixed frame counts.

**Milestone** M1.5. **Needs** issues 1, 2 and 6.

**Allowed paths** `runner/`, `harness/schema/scenario.schema.json` (format 2, keeping format 1 valid), `notes/`, `STATUS.md`

**Acceptance**
- **Tier 1:**
  - format 2 schema tests;
  - snapshot reuse with homebrew: two scenarios from one snapshot give the same results as booting each from scratch;
  - the baseline reader parses a synthetic file built from the documented structure.
- **Tier 2:** covered by issue 8.

**Note** The load sequence needs a few early M2 addresses: title screen, the game's mode, field loaded. Each one is recorded in `notes/` with its source and confirmed by a Tier 2 scenario.

## 9. Reviewer subagent

**Outcome**
- A reviewer that an implementing session starts before merging, and that the owner can start on any PR.
- It has its own definition (a prompt and a checklist).
- It reads the PR fresh and checks it against `CLAUDE.md`:
  - scope and allowed paths;
  - protected paths;
  - claims backed by tests that were run;
  - tests not weakened;
  - PR report complete.
- It runs the tests itself, and returns PASS or FAIL with findings.

**Milestone** M1.5

**Allowed paths** `.claude/agents/reviewer.md` (new), `docs/CONTINUITY.md` (merge rules), `docs/AUTOMATION.md` (reviewer section), `notes/`, `STATUS.md`

**Acceptance**
- **Recording the verdict:**
  - the verdict is posted on the PR as a comment with a fixed marker and the reviewed commit;
  - the merge rule says the verdict must be PASS on the commit being merged.
- **Dry runs** of the reviewer, recorded in `notes/`:
  - a PR with a deliberate protected-path edit;
  - a PR with an unverified claim;
  - a clean PR.

  The first two come back FAIL with the right finding; the clean one comes back PASS.

**Note** Agent sessions can't set commit statuses, so the verdict is a comment, not a required check. A later option is a small workflow on `main` that turns the marked comment into a `reviewer` status.
