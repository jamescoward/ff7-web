# #228: a world-map save loads back after a restart

Status (2026-11-21): **attempt 1 built, Tier 2 not run yet.** Second implementer, Overflow work (Trip mode rule 9).

## What was built
- **Format 2 restart step** `{ "restart": "keep-card" }` (`runner/format2.js`, `harness/schema/scenario.schema.json`, `harness/README.md`). `playScript` takes the boot point's state bytes. At a restart it reads the card, puts it back and loads that state. A save boot does the same with its generated card (#38), and loading flags the card as new (notes/31-card-and-snapshots.md). The step takes no frames, and the frame count runs on.
  - Where the state comes from: the Tier 2 boot point snapshot (`opts.snapshot`), the snapshot `runScenario` takes itself, or, for `fresh` and `sameState: "boot"`, the state saved right after the boot through T. `rerun` uses the same snapshot as the main run.
  - Load rules: a restart is allowed only in a scenario from a boot point with `card: "blank"`. It is refused from power-on, from a boot point without a card, from a named snapshot (whose chain would not be replayed), and in a boot point's own script.
- **Card check `savemap` report** (`runner/savegen/read.js` `cardOutcome`, `CARD_REPORT`): 1 if the first changed slot's savemap bytes (block + 0x200, 0x10F4 bytes) differ, else 0. This answers PR #227's reviewer note: a slot whose directory frame alone changed reads 0.
- **Tier 2 scenario** `save-boot-20d-world-save-load` (generated by `runner/test/unit/world-load-scenarios.js`). It plays save-boot-20a's script unchanged, minus the `menu_wait` metric name (8-metric limit). Then it restarts, loads as save-boot-7-world-kalm does (Circle every 30 frames until g_GameState 3, 600 frames, three Circles, window 0 reads 0, a mark, Down+Left) and checks: card_ok, c_data (savemap changed), w_state, win_ok, world_ok, map_ok (location 2), x_dir, match.
  - Why card_ok and c_data are in the same scenario: the generated save in slot 1 is also a world-map save at location 2. A load alone can't tell the game's save from ours.

## Tests
- Tier 1 unit: `format2-restart.test.js` (schema; loader refusals: no card, power-on, named snapshot, boot point script). `savegen-read.test.js` (savemap 1 on a rewrite, 0 for a directory-frame-only or icon-area change). `world-load.test.js` (generated file, script = 20a's, load = save-boot-7's).
- Tier 1 real core (`runner/test/tier1/format2.test.js` "restart steps"): on pad-echo with a card, 10 frames, restart, 5 frames ends with the same counter as 5 frames alone. This holds for the own snapshot, a shared one and fresh, and `rerun` and `boot` both match. A card set before the restart is byte-identical after it, and RAM equals a plain restore plus 5 frames.
- Existing tests changed only to expect the new `savemap` field (savegen-read, format2-card, tier1 card checks): extended, not weakened.

## Attempt 1 plan (Tier 2)
Expect save-boot-20d: card_ok 1, c_data 1, w_state > 0, win_ok > 0, world_ok 1, map_ok 1, x_dir ≠ 0, match 1. Every other scenario unchanged.

What decides attempt 2:
- `card_ok 1, c_data 0`: the game rewrote only the directory frame. That would be surprising. Then load-back proves nothing new, so investigate first.
- `w_state 0`: the title did not load file 1 after the restart (the card was not seen as new, or the cursor starts elsewhere). Check with a diagnostic: g_SaveSlotMask (save-boot-1's `slot_mask`) after the restart.
- `win_ok 0`, or `world_ok 0` after w_state > 0: the loaded save does not open the entry window, and the three Circles did something else on the world map. Next: drop the Circles and wait for the window state instead.
